# SaaS Forge Downloader: Re-Prioritized Top 20 Specs

_Date: 2026-10-04. Supersedes the ranking in `docs/superpowers/specs/2026-04-07-*` and `docs/plan.md`. The original specs stay as background reading; each new spec below says which old spec it supersedes or narrows._

## Why re-prioritize

The April ranking assumed SaaS Forge was a boilerplate repo. It is now a **boilerplate downloader**: buyers pick a product type, tier, version, platforms and paid **scaffold modules** in a wizard, pay credits, and download a compiled starter. Upgrades come later through the template branch or the Claude Code upgrade kit.

That changes what "improvement" means. A spec is worth building when it does at least one of these:

1. **Makes every download correct and trustworthy.** It compiles, it is priced correctly, and it contains only what was bought.
2. **Adds a sellable, strippable module** that buyers can toggle in the wizard.
3. **Makes the post-download and upgrade experience smoother**, which drives repeat purchases and credit top-ups.

Features that only make the root app nicer, and never reach a download, rank low.

## Defects found during the audit (they drive the top of the ranking)

- **Price shown ≠ price charged.** `packages/ui/src/lib/constants/scaffold-modules.ts` and `apps/mobile/components/downloads/constants.ts` hardcode `BASE_SCAFFOLD_CREDITS_COST = 10`, but `scaffold-modules/registry.json` has `baseCreditsCost: 20`. The wizard says "Base starter costs 10 credits" and the server charges 20.
- **Module availability drift.** The UI marks `api_keys`/`notifications` `available: false`. The registry marks them `downloadEnabled: true, implemented: false`.
- **Unselected modules still ship code.** `api_keys` has an empty manifest. The `ai` unselected manifest does not remove `apps/backend`, `Dockerfile.backend`, `docker-compose.backend.yml`, `aiJobsProcedures.ts` or `apps/web/lib/backend`.
- **No combinatorial build guard.** CI builds the root app, but no CI job compiles the module × platform variants that buyers actually download. Only `multiTenancyVariant.test.ts` covers one module.
- **Secrets transit the server.** `/api/scaffold` accepts `envVars` (including `DATABASE_URL`) and writes them into the zip. This contradicts the "never collect secrets" decision of the v1 API path.
- **CPU-heavy downloads.** Every download copies the template, applies manifests and zips at `zlib level 9` inside the request. Identical selections are rebuilt from scratch.
- **The CLI clones the wrong thing.** `scripts/cli.js` runs `git clone` on the **root** repo (the downloader platform), not the starter.

### Ranking logic

- **1–4 fix the engine before anything else is added.** Each new module multiplies the variant count. Adding modules on top of an unguarded, mispriced, CPU-heavy build path would multiply defects.
- **5–6 make the existing catalogue honest.** Buyers must get only what they paid for. Both also make the ranks below cheaper, because every new module follows the same manifest and slot pattern.
- **7–11 improve the buyer journey end to end**: what you see before paying, how you get it, how you make it run, how you upgrade, and how clean the code is.
- **12–20 are new sellable modules**, ordered by dependency (jobs come before notifications and webhooks) and by buyer demand from `docs/plan.md`.

### Deliberately deferred (outside the top 20)

- **i18n (#07).** It touches every string in every module override. Doing it before the module set stabilises would force rewrites of every `template-overrides` and `scaffold-modules/*/overrides` file. Revisit after rank 13.
- **Storage manager (#11 remainder), real-time (#18 remainder), desktop auto-update (#12 remainder), mobile push/biometrics (#05 phase 3).** These are valuable but narrower. Their foundations (secure uploads, SSE proxy, desktop/mobile screens) already exist.

## Conventions for every spec in this folder

- Each new module ships with a `scaffold-modules/<id>/manifest.json` whose `unselected` actions strip it cleanly, uses the **slot/stub rule** from the multi-tenancy spec, and is added to the variant matrix (#1).
- Prisma changes: edit the schema and run `pnpm generate`. The project owner runs `pnpm migrate`. Each migration folder goes into the module's `unselected.remove`.
- Every new API route gets a `route-policy.ts` row. Every new env var goes into the relevant `.env.example` and, if it is required by a toggle, into `INTEGRATION_REQUIREMENTS`.
- Validate with `pnpm template:check-sync`, `pnpm template:build` and the variant matrix.
