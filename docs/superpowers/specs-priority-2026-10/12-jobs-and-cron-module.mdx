# 12 — Background Jobs & Cron Module (`jobs`)

_Rank 12 · Track: new module · Effort: L · Supersedes April #06 (background jobs) and #20 (cron)_

## Context

The only queue today is the Python ARQ worker in `apps/backend`, which is scoped to AI agent/RAG jobs. In the JS stack, emails (`packages/email`) are sent inline in request handlers, there is no retry or dead-letter, and there is no scheduler. Notifications (#13), outgoing webhooks (#16), usage threshold alerts (#17), and trial/lifecycle emails all need a generic, typed, retryable job layer plus recurring triggers.

April #06 and #20 were correct but separate. Cron should enqueue jobs, not reimplement them, so they ship as one module.

## Why This Priority

It is the foundation for three later modules. Shipping it as its own strippable module (rather than baking it into the base) keeps simple starters simple, and it is a sellable item in its own right ("reliable background jobs + cron").

## Overview

Add `packages/jobs` with typed job definitions, enqueue, retry with backoff, dead-letter and a cron registry. Use Upstash QStash as the default serverless transport, an in-process driver for local development and tests, and an admin page for failures and replay.

## Main Approach

- **API**: `defineJob(name, zodSchema, handler, { retries, backoff, version })`, `enqueue(name, payload, { delay, dedupeKey })` and `defineSchedule(name, cron, jobName, payload)`.
- **Drivers**:
  - `qstash` (default): enqueue publishes to `/api/jobs/run` with a signature, which is verified with `QSTASH_CURRENT_SIGNING_KEY` / `NEXT_SIGNING_KEY`.
  - `inline` (development and tests): runs immediately in-process with the same retry semantics.
  - `redis` (self-host/Docker): a BullMQ-style worker entry for `docker-compose`.
- **Persistence**: `JobRun` (id, name, version, payload hash, status, attempts, lastError, nextRunAt) and `ScheduleRun` (name, firedAt, status). This gives the admin visibility without vendor dashboards.
- **Cron**: the registry compiles to `vercel.json` `crons` entries (generated by `pnpm jobs:sync-cron`) for Vercel, and to QStash schedules or the Redis worker for other hosts. Handlers must be idempotent (`dedupeKey = schedule + window`).
- **First jobs**: `email.send` (migrate `packages/email` senders to enqueue), `cleanup.expiredInvitations`, `cleanup.expiredSessions`.
- **Admin**: `/admin/jobs` lists failed and dead-lettered runs with replay and discard, built on `adminProcedure` and `route-policy` rows. `/api/jobs/run` uses a new `webhook`-style auth mode (signature).
- **Module**: `scaffold-modules/jobs`. When unselected, `enqueue` is a stub that runs inline (so email still sends), and the admin page, routes, `jobs.prisma` and cron config are removed.

## Deliverables

1. `packages/jobs` with drivers, typed definitions and a backoff/dead-letter policy.
2. `jobs.prisma` (`JobRun`, `ScheduleRun`), with the migration left to the owner.
3. `/api/jobs/run` and `/api/cron/[name]` routes with signature verification and policy rows.
4. Email sending migrated onto jobs, plus two cleanup schedules.
5. `/admin/jobs` page (failures, replay, schedule last/next run).
6. `scaffold-modules/jobs` manifest, registry entry and matrix coverage. Env vars added to `.env.example` and `INTEGRATION_REQUIREMENTS`.

## Likely Files / Systems Affected

- new `packages/jobs/*`, `packages/database/prisma/jobs.prisma`
- `packages/email/src/*`, `apps/web/app/api/jobs/*`, `apps/web/app/(home)/admin/jobs/*`
- `apps/web/lib/route-policy.ts`, `apps/web/lib/env.ts`, `vercel.json`
- `docker-compose.yml` (optional worker service)

## Risks / Dependencies

- Keep the Python ARQ queue for AI agents (different runtime). Document the boundary: JS jobs for product work, ARQ for graph and RAG work.
- Payload versioning: handlers receive a `version` and must handle `version - 1` during deploy overlap.
- Self-hosters without QStash must get a working path (the Redis driver) or the module is Vercel-only. Make this explicit in the wizard.

## Verification

1. Enqueuing an email returns immediately, and the email is delivered through `/api/jobs/run`.
2. A handler failing three times lands in dead-letter, is visible in `/admin/jobs`, and replay succeeds.
3. A duplicate cron trigger in the same window executes the handler once.
4. The variant without `jobs` still sends email (inline stub) and has no jobs routes or models.
